# 立体库技术与平台接口文档

版本：V0.2  
日期：2026年10月14日  
项目：warehouse_shelve  
用途：指导入库推荐、出库货位与拣货路径推荐的后续开发，并作为与仓储调度平台确认接口的依据。

本项目采用前后端分离架构，前端负责页面交互，FastAPI 后端提供 HTTP 接口和统一业务服务。Web 启动自动启动后台服务并打开登录页面，登录后进入首页；也支持从其他项目携带鉴权信息跳转，经校验后进入首页。后台启动仅启动服务，不打开浏览器，但保留前端结果页面的访问能力。平台通过同步 POST 请求调用算法；每次作业重新通过 GET 获取库存快照，并获取涉及货品的 SKU 规格。仓库布局由现有 3D 货位布局预览对应的离线数据提供。首页通过设置按钮进入算法配置，配置持久保存后立即生效；未登录不得操作设置或演示功能。

文档中的“已确认”表示用户已明确的设计要求；“建议设计”表示供开发和评审使用的方案，尚不构成客户确认的接口承诺；“待确认 Qxx”表示需与客户或平台方核实的事项。未决字段不得在实现时自行猜测。

## 1 范围和现状

### 1.1 本次开发范围

- 入库作业：根据订单、实时库存、SKU 规格和离线货位布局推荐存放货位。
- 出库作业：根据订单和实时库存确定出库货位及数量，并推荐可通行的拣货路径。
- 两种启动方式，共用业务模块和结果展示能力。
- 与平台现有入库和出库请求兼容，并调用平台库存及 SKU 查询接口。
- 增加登录页面和其他项目带鉴权跳转首页的入口，未登录不得操作设置或演示功能。
- 采用前后端分离架构，Web 页面和平台请求进入同一套后端业务服务。
- 首页新增设置按钮，分别配置入库库位推荐和出库拣货路径推荐，持久保存并立即生效；现有配置页面改为仅加载数据，不再配置算法。
- 入库、出库分别提供结果页面，每次计算的输入、配置和结果保存到 results 目录。

装车推荐、车辆配置、货量预测不属于本次开发范围。附件中的这些接口不作为本次实现要求。

### 1.2 已有能力与开发差距

现有目录为 apps、core、modules、solvers、data、results 和 doc。后续在当前业务架构内进行前后端分离：apps 承载启动入口、后端接口和前端页面资源，前端通过 HTTP 接口访问后端；modules 承载统一业务建模与服务，solvers 承载求解后端，core 承载公共数据和路径处理。前端具体技术选型及部署方式尚未确定。

| 能力 | 当前情况 | 后续要求 |
| --- | --- | --- |
| 货位推荐 | 已有启发式、COPT、OR-Tools 后端 | 适配立体库规则和平台数据 |
| 拣货路径推荐 | 已有启发式、OR-Tools；COPT 尚未实现 | 补齐 COPT，适配出库策略和立体库布局 |
| 页面与任务 | 已有 Web 页面、上传文件、结果保存与展示 | 前后端分离，增加登录、带鉴权跳转、首页设置和平台兼容接口；原配置页仅加载数据 |
| 3D 货位预览 | 已有布局展示和演示库存、演示路线 | 补足实际尺寸和通行数据，接入计算结果 |
| 平台对接 | 本文定义后续对接设计 | 不视为已实现或已通过联调 |

当前拣货货位选择以既有库存字段和货位成本等为依据，不能视为已经实现先进先出或先到期先出。配置页面也不能因展示了某求解器选项，就将尚未完成的后端视为可用。

## 2 启动方式和系统职责

### 2.1 两种启动方式

| 项目 | Web 启动 | 后台服务启动 |
| --- | --- | --- |
| 启动 FastAPI 服务 | 自动启动 | 启动 |
| 自动打开浏览器 | 是，服务就绪后打开登录页面 | 否 |
| 入库和出库 HTTP 接口 | 提供 | 提供 |
| 结果页面 | 提供 | 提供 |
| 登录及首页设置页面 | 提供，设置和演示操作必须登录 | 提供访问能力，设置和演示操作必须登录 |
| 加载已保存算法配置 | 是 | 是 |

已确认采用前后端分离。前端负责登录、首页、数据加载、设置、演示和结果展示，通过 HTTP 接口调用 FastAPI 后端；平台通过兼容接口访问同一后端。后端统一执行鉴权、数据校验、配置读取、业务建模、求解和结果保存，Web 与平台使用同一套业务服务。前后端分离不要求必须部署在不同主机，具体部署方式仍待确认 Q15。Web 手动上传输入数据的能力继续保留；演示文件求解与平台实时求解应明确标识数据来源。

启动流程为：读取运行配置 → 加载并校验算法配置 → 校验离线布局及后端可用性 → 启动服务 → Web 模式打开登录页面。登录后进入首页；其他项目携带的鉴权信息校验通过后也可进入首页。缺少必要配置或布局时，应提示具体问题，相关作业不得使用示意数据生成正式推荐。

当前桌面入口 apps/launcher.py 会选择可用本地端口，现有 Web 入口 apps/web_portal.py 可指定监听地址和端口。远程服务需要可配置的固定监听地址、端口和外部访问地址，具体值待确认 Q15。上述是现状说明；本文不新增或变更启动命令。

### 2.2 数据和职责边界

平台负责发起作业请求，并提供库存、SKU 等业务数据；后端负责鉴权、校验、单位换算、建模、求解和结果数据接口；前端负责页面交互和结果展示；离线布局负责提供货位几何、编号、层级和通行网络。

建议算法服务只输出推荐，不直接修改平台库存；平台负责库存预占、实际出入库登记和扣减。这一职责边界尚需确认 Q11。服务内用于一次求解的临时数量分配不能代替平台库存预占。

每次重新读取库存能够减少操作人员未按推荐执行造成的数据偏差，但不能保证取快照后的库存不变，也不能消除多个请求使用同一份可用库存的问题。跨请求库存占用和推荐结果执行前复核需要平台共同确认。

### 2.3 登录与访问控制

系统提供登录页面，登录成功后进入首页。首页支持从其他项目携带鉴权信息跳转，后端校验成功后建立本项目可识别的登录状态；鉴权失败不得作为已登录用户进入功能操作流程。

未登录用户不得操作设置或演示功能。前端应限制对应入口，后端也必须校验相关数据加载、演示计算和配置读写接口的登录状态，不能仅隐藏按钮。直接访问页面地址或直接调用接口不得绕过登录校验。平台服务调用继续使用平台接口鉴权，不能因为没有浏览器登录状态就视为未授权，也不能绕过其自身鉴权。

账户来源、登录凭据、会话有效期、其他项目鉴权信息的传递及校验协议、登录用户是否区分管理员权限尚未确定，归入 Q09、Q14；本文不指定具体 Token 或单点登录协议。历史结果页面的具体权限和嵌入规则继续保留 Q17。

## 3 首页设置与算法配置

### 3.1 已确认要求

首页新增设置按钮，登录后进入设置页面，分别为“入库库位推荐”和“出库拣货路径推荐”维护算法配置。支持启发式、COPT、OR-Tools，以及 timelimit、线程数等参数。配置保存到持久介质，保存成功后立即生效，无需重启；系统启动时加载已保存的配置，Web 和平台发起的新作业均使用当前有效配置。现阶段平台没有本项目算法配置，不依赖附件的算法方案列表作为配置来源。

现有配置页面改为数据加载页面，仅负责输入文件选择、上传和数据加载，不再提供求解器、时间上限、线程数等算法配置或覆盖入口。后端统一读取设置页面保存的配置，防止 Web 页面与平台调用使用不同算法参数。

### 3.2 建议配置模型

已确认按“入库库位推荐”和“出库拣货路径推荐”分别配置。出库配置覆盖货位选择与路径推荐；若需要将出库内部阶段再分别选择求解器，仍需另行确认。

| 配置项 | 建议内部字段 | 含义和校验 |
| --- | --- | --- |
| 求解器 | backend | heuristic、copt、ortools；必须具有可用实现 |
| 时间上限 | timelimit | 单位秒，有限正数；具体取值由管理员设置 |
| 线程数 | threads | 正整数；传递方式按后端实际支持能力适配 |
| 出库策略 | outbound_strategy | FIFO 或 FEFO，默认值待确认 Q05 |
| 配置版本 | config_version | 用于记录每次作业实际使用的配置 |

建议保存到运行目录下的 config/algorithm_config.json，采用临时文件写入后替换，避免写入中断破坏旧配置。保存时校验参数和后端可用性；保存失败保留旧配置。目录和字段是内部设计，不是平台既有接口字段。

保存成功后立即更新后端有效配置，使后续 Web 和平台作业无需重启即可使用新配置。建议运行中的作业继续使用开始时的配置副本，是否调整在途作业仍待确认 Q09。若采用多个后端进程，保存成功后应确保各进程对后续作业使用一致的有效配置。是否按仓库进一步区分、初始参数和登录用户的管理权限仍待确认 Q09。配置缺失或非法时，应明确提示进入设置页面配置，不默默选用某个求解器。

启发式可能没有与优化求解器完全相同的线程控制或时间截止行为。页面应说明后端对参数的实际支持情况；无效参数不能显示为已经生效。COPT 不可用或许可异常时应报告原因，不自动换成其他后端。

### 3.3 平台 algoPlanId 的处理

保留附件请求中 algoPlanId 的接收能力，但不能自动将平台方案编号映射为本项目配置，也不能静默忽略。非空 algoPlanId 的处理方式待确认 Q08，可选方案包括：映射本地已登记配置，或明确告知该方案尚未支持。未传 algoPlanId 时使用本项目已保存的有效配置。

附件中的权重和 mlMatchWeigth 不自动加入本次算法。是否需要目标权重、机器学习匹配度或多个配置方案，应另行明确后再开发。

## 4 离线布局和单位换算

### 4.1 布局数据来源

以现有 3D 货位布局预览为布局基础，不在每次作业时通过平台布局 GET 接口在线获取。建议将可计算的布局参数保存为离线数据，页面与算法读取同一版本；具体文件组织、更新方式和平台编号映射待确认 Q10。

现有预览包含 C14、C15、C16 三排货架、45 列、5 层，三排第20至22列底部两层留空，有效货位共657个。业务坐标为 X 向右、Y 从门口向墙、Z 向上；当前列宽、货架深和层高为示意单位。预览说明中的通道和门口位置是当前展示基线，不代表实测尺寸。

现有预览路线仅展示画线能力，不执行优化。不得把预览中的演示路线直接作为生产路径，也不能将示意长度报告为实际米数。

### 4.2 算法所需布局信息

| 数据 | 用途 | 状态 |
| --- | --- | --- |
| 仓库编号、货位编号、排列层 | 与库存匹配并定位目标货位 | 需确认平台映射 |
| 货位实际长宽高、承重、容量 | 判断是否能存放货物 | 由用户补充或确认适用约束 |
| 通道长度、宽度、可通行边 | 构建路径网络 | 实际尺寸待补充 |
| 通道方向和禁行规则 | 排除不可行路线 | 待确认 |
| 门、起终点、货位作业点 | 路径起终点和访问节点 | 待确认编号及业务规则 |
| 布局版本和单位 | 复现计算与结果展示 | 建议离线保存 |

高层货位应通过地面作业点连接路径网络，还是考虑高度、升降成本或其他距离，待确认 Q07。不因为存在三维坐标就自行增加设备调度或升降模型。

### 4.3 数量换算

已确认存在主单位“瓶”和订单单位“件/箱”，SKU 规格给出转换率。建议计算时统一为主单位，保留原始订单单位及转换率，返回时按确认的响应单位转换。

主单位数量 = 订单数量 × 每个订单单位包含的主单位数量。

示例：某 SKU 为12瓶/箱，订单3箱，对应36瓶。该数值仅说明换算公式，不作为任何实际 SKU 的规格。是否允许非整箱出库、余瓶如何处理、结果 num 的单位，以及库存 storedQuantity 是否确实为瓶，待确认 Q04。

附件 conversionRatio 描述的是“包装单位到基础单位”，举例为箱/托；不能直接认为它就是瓶/箱。必须确认本项目返回的转换字段、方向和适用包装层级。使用精确数值换算，不使用浮点误差导致数量丢失，也不自行取整。

SKU 尺寸和重量必须明确对应瓶、箱或外包装，并确认长度和重量单位。重量字段 storedWeight 应确认是库存行总重量还是单件重量。必要规格缺失、转换率无效、编号无法映射时，应给出可定位的数据错误，不能以0或任意默认值继续正式计算。

## 5 平台接口清单与兼容原则

### 5.1 本项目提供的接口

| 方法 | 附件示例路径 | 调用方向 | 本次用途 |
| --- | --- | --- | --- |
| POST | /createlocation | 平台 → 算法服务 | 入库货位推荐 |

两个 POST 路径来自附件 curl 示例，附件的正式请求 URL 仍为“待定”，需确认实际部署路径及前缀 Q15。结果页面路径由项目定义并与平台联调确认；不能将附件中的平台页面相对路径直接作为本服务的页面地址。

### 5.2 本项目调用的平台接口

附件示例基础地址为 http://so56.mynatapp.cc，正式地址、环境和鉴权待确认。以下路径保留附件原名。

| 方法和路径 | 参数 | 获取内容 | 采用方式 |
| --- | --- | --- | --- |
| GET /api/open/owtbmetadata/getStockInfo | warehouseId | 库存列表 | 每次入库和出库重新读取 |
| GET /api/open/owtbmetadata/getGcInfo | itemCode | SKU 规格 | 每次作业按涉及货品读取 |
| GET /api/open/owtbmetadata/getWarehouseInfo | userCode | 仓库及混放、批次、叠放规则 | 是否采用及规则来源待确认 Q10 |
| GET /api/open/owtbmetadata/getLocationInfo | warehouseId | 库位尺寸、容量等 | 在线接口与离线数据的分工待确认 Q10 |

getGcInfo 示例以逗号连接多个 itemCode。最大批量、URL长度限制、缺失 SKU 的响应方式待确认 Q12。入库计算若需判断已有库存占用尺寸或混放兼容性，涉及 SKU 不能只限于新增订单，还应包含参与容量和规则计算的已有库存货品。

getAllGcCode 默认只返回10条且没有明确翻页参数，不作为自动获取全部 SKU 的依据。getWHLayoutData 和附件第2章布局查询不作为本次在线布局来源。算法方案列表、装车及预测接口不主动调用。

### 5.3 兼容约束

外部适配层保留平台字段名称，包括 storeBatchFlag、algoPlanId 等；内部可以转换为明确的业务字段，但不得自行纠正外部字段拼写或枚举值。接口层负责请求解析和响应序列化，业务模块不依赖平台响应包装。

库存、SKU 等附件接口通常返回 code、message、data，作业和算法方案接口出现 code、msg、data。不同接口成功码和错误码不能采用未经确认的统一判断规则。成功码、ID类型和空值规则待确认 Q02。

## 6 入库作业接口

### 6.1 请求定义

POST /createlocation；Content-Type 为 multipart/form-data；附件示例使用 Authorization: Bearer {token}，鉴权细节待确认 Q14。

| 字段 | 附件类型 | 必填条件 | 说明 |
| --- | --- | --- | --- |
| warehouseId | String | 必填 | 平台仓库标识 |
| algoPlanId | Long | 可选 | 本项目处理规则待确认 Q08 |
| storeBatchFlag | Integer | 可选 | 附件为0否、1是；与混放规则的关系待确认 Q06 |
| orderType | Integer | 必填 | 0上传文件，1自定义订单 |
| file | MultipartFile | orderType=0 | Excel文件，模板待确认 Q01 |
| order | List<Object> | orderType=1 | 表单编码和实际结构待确认 Q01 |

订单行字段：orderNo 可选；itemCode、itemName、productionBatch、num 在附件中必填；unit 可选且定义为 Integer。unit 的编码与瓶、件、箱的关系待确认 Q04。productionBatch 是否允许空值以及同一订单多个相同 SKU 行的关联方式待确认 Q03、Q06。

附件提到 order 又给出含 data 的结构，未提供 orderType=1 的实际 curl 示例。因此初稿不将 JSON字符串、裸数组或包装对象中的任意一种定为已确认协议。

### 6.2 处理流程

1. 校验鉴权、字段、订单或文件结构，并生成内部作业标识。
2. 固定本次算法配置和离线布局版本。
3. 获取 warehouseId 对应的最新库存，获取涉及 SKU 的规格。
4. 校验库存仓库归属、货位映射、必要规格和单位换算。
5. 按已确认的货位容量、混放和批次规则建立模型，调用配置中的求解后端。
6. 校验推荐数量守恒、货位容量和业务限制，保存输入及计算结果。
7. 同步返回推荐结果和对应结果页面地址。

storeBatchFlag 与 skuBatchLocation、diffSkuLocation、palletStackLimit 的优先级，以及附件“均未提供则默认是”的规则是否适用于本立体库，待确认 Q06。当前不能据此推导出允许混批、禁止混批或自动按托盘分配。

### 6.3 响应定义

附件响应包装为 code、msg、data，data 内包含 recordId、pageUrl、results；results 每条包含 orderNo、itemCode、itemName、productionBatch、num、locationId。

入库示例成功码为200；recordId 在字段表中为Long、示例中为字符串；locationId 被描述为“库位名称”。这些冲突均待确认 Q02、Q03。响应 num 的单位待确认 Q04。

建议允许一条订单行拆分到多个货位，但具体是否允许拆分、如何标识原始订单行、容量不足是否返回部分结果，待确认 Q03、Q13。平台未确认前不能通过丢弃未分配数量的方式返回正常成功。

## 7 出库作业接口

### 7.1 请求定义

POST /createpick；Content-Type 为 multipart/form-data。warehouseId、algoPlanId、orderType、file、order 的规则与入库相似，但附件将出库 order 类型写为 Object，同时举例为 data 数组，需确认 Q01。

订单行字段：orderNo 可选；itemCode、itemName、productionBatch、num 为附件必填；locationCode、unit 可选。指定 locationCode 时是否禁止从其他货位补货、生产批次与出库策略如何共同生效，待确认 Q03、Q06。

### 7.2 出库策略

已确认业务策略应为先进先出或先到期先出。建议由管理员配置选择策略，不将当前代码的货位成本排序直接当成批次策略。

| 策略 | 需要的数据 | 待明确的规则 |
| --- | --- | --- |
| FIFO 先进先出 | 库存入库时间及库存行标识 | 同时间排序、批次限制、指定货位的优先级 |
| FEFO 先到期先出 | 有效期截止时间或可推导到期时间的生产日期与保质期 | 过期品是否排除、同到期日排序 |

附件库存字段只有 productionBatch 和 inboundTime，未给出到期日期。不能从生产批次字符串自行推导到期时间。FEFO 数据来源和字段待确认 Q05。

附件 outboundStrategy 字段表写1先进先出、2先到期先出，示例却使用0和1，不能自动采用任意一套编码。该平台枚举如需兼容，应明确映射到内部 FIFO、FEFO。

出库接口 storeBatchFlag 沿用“入库”描述，真实含义未确认。用户确认了先进先出和先到期先出的业务方向，但并未明确该字段的枚举和优先级；保留为 Q06，不直接改名或重解释。

### 7.3 处理流程

1. 校验请求，固定算法配置和离线布局版本。
2. 获取最新库存及相关 SKU 规格，完成单位和货位映射。
3. 按确认的可用数量、指定货位和批次限制筛选候选库存。
4. 按 FIFO 或 FEFO 及已确认的同优先级规则分配出库数量。
5. 根据选定货位作业点、可通行网络和起终点生成路径。
6. 校验数量不超库存、不重复分配，路径连续、方向正确且能够访问选定作业点。
7. 保存输入、货位推荐、路径顺序和求解信息，同步返回结果页面及兼容响应。

一单一路线、合单波次、起终点选择、设备容量以及货位选择与路径联合优化的范围待确认 Q07。建议先定义库存与出库策略硬约束，再明确距离优化目标；不能为缩短距离违反确认的出库规则。

### 7.4 响应定义

附件示例为 code=0、msg、data；data 包含 results、pageUrl、recordId。results 包含 algoId、warehouseId、locationId、itemCode、itemName、productionBatch、orderNo、num。

字段说明额外列出 exitId 和 routePointIds，响应示例未展示，routePointIds 被定义为 String。它们的实际层级、字符串分隔方式或数组结构、点位编码、顺序和多路线组织均待确认 Q07。本文不将建议路线对象作为既有平台协议。

建议内部保存有序路径点、停靠货位、对应拣货数量和累计距离，确认后再适配外部返回格式。结果页面应展示出库货位、数量、批次、访问顺序与路径，并标注该结果使用的库存获取时间。

## 8 库存和 SKU 数据协议

### 8.1 库存快照

getStockInfo 输入 warehouseId；附件库存行包括 warehouseId、locationId、itemCode、productionBatch、itemName、orderNo、storedQuantity、storedWeight、itemUnit、inboundTime。

附件 storedQuantity 是可选字段，但出库计算必须有可靠可用数量；字段缺失不能当成零库存。需确认 storedQuantity 是账面量还是已扣预占的可用量，有无冻结或锁定数量，以及空列表和未知仓库的差别 Q11、Q12。

接口描述为单仓库全量库存，示例却包含不同 warehouseId。正式实现应验证响应仓库归属；混入其他仓库的数据不能参与计算。库存行唯一标识、重复行合并规则、分页、完整性、快照时间或版本均待确认 Q12。

### 8.2 SKU 规格

getGcInfo 输入 itemCode；附件返回基础单位尺寸重量、packagingType、packagedLength、packagedWidth、packagedHeight、packagedWeight、packagingUnit、conversionRatio、applicableScenario 等字段。

本项目优先明确瓶与箱/件的换算和算法所需的存放包装规格。附件中的托盘、半托字段只有在本项目实际采用对应作业方式时才纳入，不因文档中存在字段就扩大功能范围。

每次作业重新获取规格，建议将原始返回和标准化结果一并保存。重复 SKU 可在同一次作业内合并查询，但不得以之前某次推荐结果代替本次库存快照。

### 8.3 数据获取失败

平台超时、鉴权失败、业务错误、数据缺失、返回结构错误应分别记录，说明失败环节。正式平台作业不得自动回退到示例 CSV 或历史库存继续计算。

GET 查询超时和有限重试可以作为运行配置；次数、等待时间和平台访问限制待确认 Q12、Q15。POST 作业是否可重试与幂等规则有关，不套用 GET 重试策略。

## 9 同步执行与后续异步方向

### 9.1 本期同步方式

一次 POST 包含读取实时数据、校验、求解、保存和返回。只有完成本次处理后才向平台返回结果。FastAPI 层需要避免长时间计算阻塞其他请求；执行机制复用现有任务能力进行适配，具体并发数量依据部署资源确定。

timelimit 是算法求解时间上限，HTTP 总耗时还包含排队、数据查询、预处理和结果保存，不能将两者等同。平台、网关和服务的超时时间应协调；最大订单规模和超时预算待确认 Q15。

### 9.2 同步方式存在的问题

- 长计算持续占用连接，平台或网关可能先超时。
- 平台超时不等于算法已停止；服务可能仍在计算或已经保存结果。
- 超时后重复 POST 可能创建多个作业，返回不同库存快照对应的结果。
- 排队和数据查询增加总时长，单独限制求解时间无法保证请求总耗时。
- 连接中断后，平台难以知道作业状态，也难以恢复获取已完成结果。

求解达到时间上限但有可行解时，是接受可行解并标注非最优，还是视为失败，待确认 Q13。未找到可行解不能包装为成功空结果。

### 9.3 后续可能增加异步接口

后续可考虑“提交作业 → 返回任务编号 → 查询状态 → 获取结果”，必要时增加回调。异步接口与同步接口并存，保持原调用方兼容。状态查询路径、状态码、回调鉴权和平台支持情况另行协商，本期不承诺实现。

内部建议保存已受理、数据准备、求解中、完成、失败等状态，便于排查同步超时和将来扩展；这些状态不自动成为平台现有状态枚举。

## 10 重复请求和结果保存

### 10.1 重复请求

需确认平台能否提供唯一请求编号 Q16。“重试取同一个结果”与“主动重新计算”需要区分：前者应关联原作业，后者应创建新作业并重新获取库存。

不能仅以订单号判断重复，因为订单号可选，同一订单也可能合法重新计算。内容哈希也不能独立决定是否复用结果，因为相同订单在不同库存下可能需要不同推荐。

### 10.2 每次作业保存的信息

所有求解结果保存在 results 下，建议复用现有 results/web_jobs/<内部作业编号>/ 组织方式，平台发起作业也使用统一保存机制。

| 内容 | 保存用途 |
| --- | --- |
| 订单原文或上传文件、标准化订单 | 追溯请求和解析结果 |
| 原始库存及获取时间、标准化库存 | 复现实际计算依据 |
| SKU 规格及换算率 | 复核单位和容量 |
| 算法参数副本及版本、布局版本 | 明确本次使用配置 |
| 货位推荐、出库数量、路线明细 | 展示和下载结果 |
| 求解状态、实际耗时、错误信息 | 排查问题 |
| 平台响应和内部作业编号映射 | 追踪兼容字段 |

不保存 Authorization Token。保存期限、清理策略和访问控制待确认 Q17，不引入未确认的自动删除。失败作业也应留下足够的诊断信息，不将失败结果展示为正常推荐。

### 10.3 结果页面

入库和出库分别提供结果页面。页面展示本次推荐、库存快照获取时间、算法参数和布局版本，并接入已有3D预览。管理员配置更新或库存变化后，历史结果仍使用当次输入和布局依据，不随当前数据变化而重画成另一份结果。

结果页面由前端展示，通过后端接口获取已保存的结果。pageUrl 的绝对或相对形式、外部域名、iframe 嵌入、结果页面的登录及访问权限、有效期和页面是否需编辑功能待确认 Q15、Q17。设置及演示功能必须登录的要求已确认，不能以结果页面权限未确定为由放开这些操作。后台模式不打开浏览器，但应保留对应前端结果页面和后端数据接口的访问能力。

4. 实现库存与 SKU 获取、字段校验和标准化适配。
5. 适配入库模型和出库 FIFO、FEFO 规则，补齐所需求解后端。
6. 实现两个同步兼容接口，统一保存和结果页面。
7. 使用客户样例联调，验证超时、重试及多请求场景。

apps 中组织前端页面资源、启动和后端接口，前端通过 HTTP 访问后端；core 中实现必要的数据适配及配置读写；modules/slotting 与 modules/picking_path 中实现 Web 和平台共用的业务规则；solvers 中实现对应后端。不顺手重构无关代码，不以本次文档工作代替代码实现。

### 11.2 验收场景

| 场景 | 验收标准 |
| --- | --- |

| 异常数据 | 规格缺失、编号未知、断网、库存不足给出明确结果，无示例数据回退 |
| 同步超时和重试 | 能区分平台超时与计算失败，重复请求处理符合约定 |
| 结果保存 | 输入、参数、布局依据和结果可追溯，历史结果不被新作业覆盖 |
| 平台兼容 | 使用平台真实multipart请求及响应解析验证字段、类型、成功码和页面嵌入 |

## 12 客户与平台待确认清单

本节可以直接用于逐项沟通。建议每项补充“确认结论、确认人、确认日期、实际请求或响应样例”，确认后更新正文对应章节。阻塞平台联调的字段不得仅凭示例或字段表单方面确定。

### Q01 请求编码和 Excel 模板

确认入库和出库 orderType=1 时 order 的multipart编码，是JSON字符串、数组还是含data的对象；确认Excel工作表、表头、数据类型、单位、空值和最大文件规模。需要分别提供两种作业、两种orderType的真实可用请求样例。

### Q02 成功码错误码和 ID 类型

确认入库成功200与出库成功0是否属实；各GET接口成功码；错误码与HTTP状态码的关系；msg和message的使用；recordId、algoId和algoPlanId应是数字还是字符串，谁生成、是否要求全局唯一。长ID如何避免前端数字精度丢失。

### Q03 仓库货位和订单行标识

确认warehouseId、warehouseCode、库存locationId、请求locationCode、结果locationId、3D货位编号及平台布局元素id的映射；结果是否需要名称和ID同时返回；缺少orderNo时怎样追踪订单行；相同SKU批次多行、拆分多货位如何关联原行。

### Q04 单位和包装规格

确认瓶/件/箱的编码与转换字段，conversionRatio是瓶/箱还是箱/托；storedQuantity和num的单位；能否拆箱、允许小数及舍入规则；尺寸重量的单位及对应包装层级；storedWeight是否为总重量。

### Q05 FIFO 和 FEFO

确认默认出库策略、管理员可配置范围、平台枚举；FIFO排序依据和同时间规则；FEFO到期字段来源、缺少到期数据时的处理，以及过期品是否可出库。不得根据批次字符串自动推断到期时间。

### Q06 批次指定货位和混放规则

确认出入库storeBatchFlag实际含义、默认值和生产批次必填条件；指定批次、指定locationCode与FIFO/FEFO谁优先；是否可从其他货位补足；skuBatchLocation、diffSkuLocation、palletStackLimit是否适用，规则从哪里获取。

### Q07 路径返回和作业组织

确认exitId、routePointIds的响应层级、类型、顺序和点位映射；单订单还是合并波次；起终点如何指定；是否有人员/设备容量；层高是否影响距离或成本；高层货位作业点；货位选择和路径优化的目标与顺序。需要包含路径字段的完整响应样例。

### Q08 平台算法方案编号

确认本项目没有平台配置时，收到非空algoPlanId应如何处理；是否需要本地映射，还是返回明确未支持提示；附件的权重和mlMatchWeigth是否需要支持。

### Q09 管理员配置

已确认：首页设置按入库库位推荐和出库拣货路径推荐分别维护配置，持久保存并立即生效；设置和演示操作必须登录，原配置页仅加载数据。仍需确认是否进一步按仓库维护、初始求解器及时间上限和线程数、登录用户是否区分管理员权限。建议运行中的作业保持原配置，是否影响在途作业仍待确认。

### Q10 离线布局和规则数据

补充实际货位和通道尺寸、承重、容量及单位；确认离线文件组织、版本更新和仓库编号映射；getLocationInfo及getWarehouseInfo是否仍需调用，若不调用对应属性和规则如何离线提供；是否需要数据变更通知接口，离线布局变更由谁维护。

### Q11 库存预占和并发职责

确认算法仅输出建议，平台负责预占和实际扣减；storedQuantity是否已经排除预占、冻结；跨请求重复分配如何避免；结果执行前是否复核库存；是否有库存版本和结果失效条件。

### Q12 实时 GET 接口完整性

确认库存是否全量、是否分页、是否提供快照版本与时间、是否存在跨仓库数据；库存行标识和重复行处理；SKU最大批量、字段缺失和未找到货品的响应；GET超时、重试和访问频率限制。

### Q13 部分结果与求解状态

确认入库容量不足或出库库存不足时整单失败还是允许部分推荐；缺货或未分配明细的响应结构；达到timelimit有可行解是否接受；未找到可行解、模型无解、不可达路径如何区分和返回。

### Q14 Token 和接口鉴权

确认平台调用算法与算法调用平台各自的Token来源、请求头、校验方式、有效期、刷新方式和权限范围；是否需要租户或userCode字段。不要默认两方向复用同一个Token。

### Q15 部署地址超时和页面嵌入

### Q16 重试与重新计算
