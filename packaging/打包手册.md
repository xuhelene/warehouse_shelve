# 打包手册

把 Web Portal 打包成 Windows 免安装程序，交给没有 Python 环境的同事做客户演示。
本手册面向维护者（你自己）；给同事看的是 `packaging/使用说明.txt`。

---

## TL;DR — 代码更新后重新打包

在**项目根目录**开 PowerShell，三步：

```powershell
# 1. 打包（约 1 分钟）
powershell -ExecutionPolicy Bypass -File packaging\build.ps1

# 2. 验证（见下面「打包后必做的验证」，别跳过）

# 3. 压缩 dist\仓储优化演示 整个文件夹，发给同事
```

产物在 `dist\仓储优化演示\`，约 250MB。

---

## 一、前置条件（只需配置一次）

| 项 | 要求 | 说明 |
|---|---|---|
| 基础解释器 | Python 3.9+ | 默认用 `C:\Users\xuhel\anaconda3\envs\python39\python.exe` |
| 构建环境 | `.venv-build/` | 脚本首次运行时自动创建，已在 `.gitignore` 里 |
| 磁盘空间 | ≥ 3GB | `.venv-build` 约 500MB，`build/` 中间产物 + `dist/` 各约 250MB |

**基础解释器换了路径**，给脚本传参即可：

```powershell
powershell -ExecutionPolicy Bypass -File packaging\build.ps1 -BasePython "D:\python39\python.exe"
```

> ⚠️ **不要用 conda 环境直接打包。** conda 的 numpy 链接 MKL，PyInstaller 收不全
> `mkl_intel_thread.2.dll`，打出来的 exe 一启动就是
> `Intel MKL FATAL ERROR: Cannot load mkl_intel_thread.2.dll`。
> `build.ps1` 专门建 `.venv-build` 用 pip 装依赖（OpenBLAS 版 numpy）就是为了绕开这点。
> `-BasePython` 只是用来**创建** venv 的，本身可以是 conda 解释器。

## 二、标准打包流程

### 1. 确认代码状态

```powershell
git status                  # 确认要打包的改动都在
python -m pytest -q         # 基线：1 failed（home 页 <style> 断言，已知）+ 其余全过
```

沙箱环境下 tmp_path 会报权限错，加 `--basetemp` 指到可写目录即可：
`python -m pytest -q --basetemp="$env:TEMP\pytest_tmp"`

### 2. 依赖有变化时，先同步构建环境

只改了业务代码 → 跳过这步，`build.ps1` 会直接复用已有的 `.venv-build`。

**改了 `requirements.txt`** → 必须重建，否则打进去的还是旧依赖：

```powershell
Remove-Item -Recurse -Force .venv-build
```

下次 `build.ps1` 会自动重新创建并按新的 `requirements.txt` 安装。

### 3. 执行打包

```powershell
powershell -ExecutionPolicy Bypass -File packaging\build.ps1
```

脚本做四件事：准备 `.venv-build` → 清理 `build/`+`dist/` → 跑 PyInstaller → 把
`使用说明.txt` 拷进产物目录，最后打印体积。

> ⚠️ **产物只有 `dist\仓储优化演示\`。** `build\warehouse_demo\` 下也有一个同名 exe，
> 那是没带依赖的中间引导程序，双击必然闪退（报 `Failed to load Python DLL`）。
> `build\` 可以随时删，下次打包会重建。

正常输出结尾：

```
打包完成：...\dist\仓储优化演示 （约 251 MB）
把整个「仓储优化演示」文件夹压缩成 zip 发给同事即可。
```

**体积明显超过 300MB 说明 spec 的 `excludes` 失效了**，见第五节。

## 三、打包后必做的验证

打包成功 ≠ 能跑。PyInstaller 的问题基本都在运行时才暴露，每次都要实测。

**关键：换个目录测，不要在项目里测。** 在项目目录下跑，`_internal` 里缺的文件会被
项目里的同名文件"救回来"，测不出真问题。

```powershell
# 复制到一个干净目录（模拟同事的电脑）
Copy-Item -Recurse "dist\仓储优化演示" "$env:TEMP\demo_test\"
cd "$env:TEMP\demo_test\仓储优化演示"
.\仓储优化演示.exe
```

逐项确认：

- [ ] 黑窗口出现中文横幅，显示演示地址和结果目录，**没有 Traceback**
- [ ] 浏览器自动打开，首页五个模块卡片都在
- [ ] 五个模块各跑一次（默认数据，直接点"开始求解"）：
      货位推荐 / 拣货路径优化
- [ ] 结果确实写在 **exe 同级**的 `results\web_jobs\<任务号>\outputs\`
- [ ] `_internal\results\` 里只有 `slotting_solution.csv`，没被写脏
- [ ] 关掉黑窗口，服务停止

测完清理：

```powershell
Remove-Item -Recurse -Force "$env:TEMP\demo_test"
```

## 五、改了哪些代码要额外当心

绝大多数业务改动（modules/、solvers/ 里的建模逻辑）直接重打包就行。下面几类要多看一眼：

### 新增了第三方依赖
1. 加进 `requirements.txt`
2. 删掉 `.venv-build` 重建
3. 打包后**一定要在干净目录实测**——有些包（带 C 扩展、靠 `__file__` 找数据文件的）
   PyInstaller 收不全，需要在 spec 里补 `hiddenimports` 或 `collect_all`

### 新增了数据文件 / 模板 / 静态资源
`packaging/warehouse_demo.spec` 的 `datas` 是白名单，**新目录不会自动打进去**。当前收了：

```
data/                        -> data/
apps/templates/              -> apps/templates/
apps/static/                 -> apps/static/
results/slotting_solution.csv -> results/    # picking-path 的默认库存输入
```

### 新增了优化模块
除了 CLAUDE.md 里说的接 Web Portal 三处，打包侧还要：
- 新模块的默认输入目录若不在 `data/` 下，补进 spec 的 `datas`
- 新模块默认后端若是 `copt`，考虑在 `apps/web_jobs.py` 的 `FROZEN` 分支里改成 `ortools`

### 动了路径相关的代码
打包版有两个根目录，由 `core/paths.py` 区分，**不要再写 `Path(__file__).parents[1]`**：

| 函数 | 指向 | 用途 |
|---|---|---|
| `resource_path(x)` | `_internal/`（只读） | 模板、静态文件、随包发的样例数据 |
| `runtime_path(x)` | exe 同级（可写） | `results/` 下的任务产物、上传文件 |
| `default_input_path(x)` | 先运行目录、后 `_internal` | 默认输入（同事可在 exe 旁放同名文件覆盖） |

源码运行时三者都等于项目根目录，所以本地跑看不出区别 —— 这类改动必须打包后实测。

### spec 里的 excludes 别随手删

```python
"torch", "torchvision", "torchgen", "functorch", "onnxruntime",
"scipy", "networkx", "sympy", "PIL",
"pkg_resources", "jaraco", "backports",
```

- 前两行：`ortools` 的子模块会递归拖进 `scipy → networkx → torch`，**首版打出 720MB**，
  排掉后 250MB。本项目一个都不用。
- 第三行：`pkg_resources` 只被 `packaging`/`pytz` 的可选分支引用，但它的 runtime hook
  会去 import `jaraco` → `backports`（本环境没装），**冻结后启动直接失败**。

反过来，`setuptools` **不能**排除 —— 排了同样会让 pkg_resources 的 hook 崩。

## 六、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 双击闪退，命令行跑能看到 `Failed to load Python DLL ..._internal\python39.dll` | **跑的是 `build\` 里的中间 exe**，不是产物 | 改跑 `dist\仓储优化演示\仓储优化演示.exe`；`build\` 只是中间目录，可以随便删 |
| `Intel MKL FATAL ERROR: Cannot load mkl_intel_thread.2.dll` | 用 conda 环境打的包 | 删 `.venv-build` 重建，确认 `build.ps1` 用的是 venv 里的 python |
| `ModuleNotFoundError: No module named 'jaraco'` / `'backports'` | `pkg_resources` 的 runtime hook 被打进去了 | 确认 spec 的 excludes 里有 `pkg_resources`、`jaraco`、`backports` |
| 启动闪退、看不到报错 | 黑窗口一闪而过 | 在 PowerShell 里手敲 `.\仓储优化演示.exe` 运行，错误就留在窗口里 |
| `ModuleNotFoundError: No module named 'xxx'` | 新依赖没被收集 | spec 的 `hiddenimports` 加 `"xxx"`，或用 `collect_all("xxx")` |
| 页面样式全丢 / 三维预览空白 | `apps/static` 没打进去 | 检查 spec 的 `datas`，确认 `_internal/apps/static/` 存在 |
| `Default file not found: data/...` | 默认数据没打进去 | 同上，检查 `_internal/data/` |
| 体积突然涨到 500MB+ | excludes 失效 | 看 `build/warehouse_demo/xref-warehouse_demo.html`，搜大包被谁引入 |
| `Unexpected token ')' in expression` | `build.ps1` 存成了无 BOM 的 UTF-8 | PowerShell 5.1 按 ANSI 读中文注释会崩，**`.ps1` 和 `.txt` 必须存 UTF-8 带 BOM** |
| 同事说 COPT 报错 | 演示机没有 COPT 许可（正常） | 让他改选 OR-Tools 或 Heuristic；打包版默认已是 ortools |
| 杀毒软件拦截 | PyInstaller 常见误报 | 加白名单；或让同事点"允许运行" |

排查大依赖来源，看交叉引用报告里谁 import 了它：

```powershell
# build\warehouse_demo\xref-warehouse_demo.html 里搜 <a name="包名"> 的 imported by
start build\warehouse_demo\xref-warehouse_demo.html
```

## 七、涉及的文件

| 文件 | 作用 | 会不会经常改 |
|---|---|---|
| `packaging/build.ps1` | 一键构建脚本 | 基本不动 |
| `packaging/warehouse_demo.spec` | PyInstaller 配置（datas / hiddenimports / excludes） | 加依赖或数据目录时要改 |
| `packaging/使用说明.txt` | 随产物发给同事的说明 | 模块或操作方式变了要更新 |
| `apps/launcher.py` | 打包入口：选端口、起服务、开浏览器 | 基本不动 |
| `core/paths.py` | 只读资源根 / 可写运行根的区分 | 基本不动 |
| `solvers/copt_runtime.py` | COPT 不可用时的中文提示 | 基本不动 |
| `requirements.txt` | `.venv-build` 的依赖来源 | 加依赖时改，改后必须删 `.venv-build` |

调试用的隐藏参数：`.\仓储优化演示.exe --no-browser` 起服务但不弹浏览器。
